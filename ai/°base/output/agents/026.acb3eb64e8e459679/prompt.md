## Background

`scripts/°base/ai/hooks/record-memory/hook.py` mirrors Claude Code's per-project memory files between two locations:
- **Source** (external, outside the repo): `~/.claude/projects/<encoded-repo-path>/memory/<name>.md` (`_encoded_project_dir()`, hook.py:39-44).
- **Destination** (git-tracked mirror inside the repo): `ai/°base/memory/<name>.md` (or `ai/memory/...` for consuming repos), via `_memory_dirs()` (hook.py:47-50).

It fires only on `PostToolUse` matcher `"Write|Edit"` (single-file sync of whatever `tool_input.file_path` was touched, hook.py:323-335) and on `SessionStart` (full catch-up resync via `_sync_all()`, hook.py:337-342). Files are mirrored via hardlink (`os.link`), falling back to `os.symlink` cross-filesystem (`_sync_file()`, hook.py:60-84).

**Critical history**: the hook originally DID auto-delete the repo-side file whenever the external source file went missing. This caused a real data-loss incident (commit `d1b384a`) where an encoding bug in `_encoded_project_dir()` made the hook think the source directory was empty, and it deleted real, wanted memory files from the repo. The fix (plan `ai/°base/plans/007_prevent-accidental-memory-deletion.md`, commit `e12db5f`) deliberately reversed this: **the repo copy is now authoritative**. Current `_sync_all()` (hook.py:113-139):
- If the external source is missing but the repo copy exists → **recreates** the external file from the repo copy (hook.py:134-138). This is the opposite of deletion-propagation, and is intentional/documented, to prevent another false-positive wipeout.
- The ONLY way a repo-mirror file is removed is via a git commit whose message contains a standalone `Deleted Memory: <name>.md` line (checked via `_is_marked_deleted()`/`_has_memory_delete_marker()`, hook.py:92-103) — and even then, that just cleans up the stale *external* copy to match, it doesn't originate deletions.
- The sanctioned way to *originate* a deletion is `scripts/°base/ai/memory/delete.py` (94 lines): it unlinks BOTH the repo copy and the external source copy, then does `git add` + `git commit --only <repo-path> -m <subject> -m "Deleted Memory: <name>.md"` (delete.py:74-91). A pre-commit hook `scripts/°base/git/hooks/commit/require_memory_delete_marker.py` enforces that any commit deleting a `ai/**/memory/*.md` file carries this marker.

**The actual bug**: `delete.py` is never invoked by anything automatically — it's a manual CLI tool, undocumented in `CLAUDE.md`/`AGENTS.md`, that an agent has to know to run by name. In practice, an agent (or user) just runs `rm <path>` via the `Bash` tool on the external source file directly. Since there's no `PostToolUse` hook matcher for `Bash`/`shell`/`unified_exec` at all for `record-memory`, nothing observes this, and the repo mirror is left stale — worse, the NEXT `SessionStart` resync will actively *recreate* the external file from the (stale, should've-been-deleted) repo copy, since that's the documented safe-by-default behavior. So deletions silently never propagate, and manually cleaning up the repo copy separately (e.g. via `git rm`) risks the deletion commit lacking the required marker, or getting silently squashed away during later history cleanup (since it wasn't a dedicated, tagged commit) — this literally happened in the current chat session.

**Reference for existing Bash-command-parsing conventions in this codebase**: `.claude/hooks/permission-check.py` already parses raw Bash `tool_input.command` strings for a `PermissionRequest` hook — see its pattern for extracting the command (`tool_input.get("command") or tool_input.get("cmd") or data.get("command")`, ~line 135-139), splitting on shell control operators (`&&`, `||`, `;`, `|`), and `shlex.split()`-ing each sub-command to get argv.

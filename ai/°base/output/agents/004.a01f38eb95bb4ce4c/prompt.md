## Requirement 5 — MCP tool/cmd merge strategy fix (the meaty one)
I found and confirmed the actual bug empirically: the repo's real `ai/tool-settings/settings.json` currently has an uncommitted local diff where `mcp.servers.bugsink` — originally authored as `{"type": "stdio", "tools": [".env"], "cmd": ["npx", "-y", "bugsink-mcp"], "enabled": false}` — got flattened by a real sync run into `{"type": "stdio", "cmd": ["npx","-y","envmcp","--env-file","ai/.env","npx","-y","bugsink-mcp"], "enabled": true}`, losing the `tools` reference. Root cause is in `_merge_mcp_native_additions` (cli.py): when native files (`.mcp.json` / `.codex/config.toml`) are parsed back via `parse_claude_mcp`/`parse_codex_mcp_toml`, the result is always a FLAT entry (only `type`/`cmd`/`enabled` — no `tools` concept exists in native formats). The merge function resolves both the existing (authored, possibly tools-based) entry and the new (flat) entry to argv via `_resolve_server_argv` and compares `(argv, enabled)` tuples; if they differ AT ALL (e.g., only `enabled` toggled — argv unchanged) it does `servers[name] = entry`, wholesale replacing the authored tools-based entry with the flat native one. There's an existing regression test `test_load_layer_keeps_authored_tools_form_when_native_mcp_matches_resolved_output` that only covers the "nothing changed" case, and `test_load_layer_merges_codex_mcp_enabled_flag_change` which covers an enabled-flag change but on a server that was flat-authored from the start (no `tools` field) — so it doesn't exercise the actual bug.

- a) "detect the case of inlining a tool directly" — detect when a native/flat `cmd` array is (a prefix of, or wholly) a known tool's resolved cmd snippet.
- b) "detect matching existing tools to extract them from cmd" — the extraction algorithm itself.
- c) "improve merge strategy to not be weird" — don't lose authored `tools` structure on every native round-trip.

My proposed fix, please validate/refine:

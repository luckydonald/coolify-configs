# Git branch-split Phase 3: bootstrap a branch from clean-only

## Context

Phases 1-2 (implemented, merged as `629b51c`/`c4e6a95`) assume a branch is already flowing through the split workflow (i.e. `ai/UNCLEAN/{branch}` is the thing being actively worked on, with `{branch}`/`ai/history/{branch}` derived from it). The user now has the opposite starting condition: an existing plain `{branch}` (clean-format) with real human commits, and no `ai/UNCLEAN/{branch}` or `ai/history/{branch}` at all — they want a way to "get it started" from that clean branch.

Research (via Explore agent) found this is almost entirely already handled by existing Phase 2 code, with two small, well-scoped gaps:

1. **`sync_unclean.reconstruct_unclean` already tolerates a missing `history` branch correctly** — `_new_shas_since_cursor` returns `[]` for a `None` tip, every clean commit buckets as unmatched/code-only, and the new `ai/UNCLEAN/{branch}` is correctly built by replaying each clean commit's own diff onto a base forked from `main_branch`. No new merge/tree logic is needed here.
2. **The `refs/base-split/history-master-fork-point/{branch}` ref is a confirmed, real gap independent of this bootstrap scenario**: the Phase 2 plan assigns `sync_splits.ensure_branch_started` (`scripts/°base/git/°split_lib/sync_splits.py:52-69`) as the writer of this ref whenever it creates a `history` branch fresh, but it never actually writes it. `history_master.py` already has a `merge_base` fallback for when the ref is absent (`history_master.py:473-482`), so nothing crashes today, but the fallback is strictly worse (fragile if `ai/history/master` has since been rebased) than just fixing the writer. Fix this regardless of Phase 3, since normal forward-flow branches are missing it too.

So Phase 3 is a small, additive piece: fix the ref-writing gap, then add a thin `bootstrap-branch` command that sequences the existing pieces (ensure `ai/history/master` exists → create an empty `ai/history/{branch}` with the fork-point ref → call the already-working `reconstruct_unclean` to build `ai/UNCLEAN/{branch}`).

## The invocation paradox: the tool itself is AI/base content

`scripts/°base/git/split.py` lives under a `°base` path, so it's classified as AI/base content (`classify.is_ai_base_path`) and by definition never exists on a clean checkout. Two related but distinct cases:

- **The target repo already has `base` merged in somewhere** (e.g. `master`, an `ai/UNCLEAN/*` branch): since all git plumbing here resolves the target repo via `cwd` (`git_ops.repo_root()` does `git rev-parse --show-toplevel` from cwd), not via the script's own location, you can run the tool from a **separate worktree** of the same repo checked out to a branch that has it (`git worktree add ../repo-tools master`), invoking it by path while your shell stays on the clean checkout: `cd /clean/checkout && python3 ../repo-tools/scripts/°base/git/split.py ...`. Confirmed working — this is exactly the pattern used during Phase 1/2 verification (script path outside the target repo, `cwd` pointed at it).
- **The target repo never merged `base/base` in at all**: no in-repo copy of the tool exists on any branch, so the worktree trick doesn't apply on its own. Confirmed this requires **zero changes to `master`**: `_pull_master` only ever fast-forwards `master` to `origin/{main_branch}` (`history_master.py:162-171`), and the base/base fold (`_fold_base`/`_complete_base_fold`) exclusively targets `ai/history/master`'s tip, never `main_branch` — so the first `update-history-master` run creates `ai/history/master` from `master`'s current tip (pure ancestry) and folds `base/base` only into that new branch. `master` — and therefore every `{branch}` (clean) — never receives base/AI content, even during first-time adoption. This is a hard invariant, not an incidental side effect, and gets an explicit regression test (see below).

### A standalone, curl-pipeable launcher solves this concretely

Per the user's direction: a single self-contained script, servable raw from GitHub and safe to run repeatedly from any branch of any repo (with or without `base` ever merged in), that (1) adds/fetches the `base` remote, (2) sets up a local worktree so the real tooling becomes reachable without touching the current checkout, and (3) delegates to the real CLI.

- **New file `scripts/°base/git/get-base.py`** — stdlib-only (no imports from `°split_lib`, since none of that exists yet when fetched standalone via pipe), so it must NOT be named/structured as part of the `°split_lib` package. Usage:
  ```
  curl -fsSL https://raw.githubusercontent.com/luckydonald/base/master/scripts/°base/git/get-base.py | python3 - bootstrap-branch feature
  ```
  or locally: `python3 scripts/°base/git/get-base.py update-history-master --yes`.

  What the curl-piped line does, piece by piece (worth keeping verbatim since it's non-obvious):
  1. `curl -fsSL <url>` downloads the raw `get-base.py` file from GitHub over HTTPS. `-f` fails silently on HTTP errors (so a 404 doesn't get piped into python as if it were code), `-s` suppresses progress output, `-L` follows redirects (GitHub's raw URLs sometimes redirect).
  2. `| python3 -` pipes that downloaded script straight into `python3`'s stdin; the trailing `-` tells `python3` "read the script from stdin" rather than from a file — nothing touches disk, the script runs directly from the pipe.
  3. `bootstrap-branch feature` are extra arguments after the script content. Since `python3 -` also accepts `sys.argv` after it, everything after `-` becomes `sys.argv[1:]` inside `get-base.py`. Per step 5 below, `get-base.py` does its own setup and then hands off via `os.execvp` to the real `split.py`, forwarding these same args — so `bootstrap-branch feature` ends up being the subcommand actually executed by the real tool once it's reachable.

  Net effect: one command, run from anywhere inside any git repo on any branch, that transparently provisions the tooling (if not already present) and then runs `split.py bootstrap-branch feature` against that repo — without the current checkout ever needing to contain any of this code.

  The local form does the same thing without the curl step, piece by piece:
  1. `python3 scripts/°base/git/get-base.py` runs the script as a normal file (only possible if a copy already exists on disk somewhere reachable — e.g. after a first curl-piped run, or a worktree/checkout that already has `base` merged in). `update-history-master --yes` are just the trailing args: `python3 <script> arg1 arg2` sets `sys.argv = [script, arg1, arg2]`, so `sys.argv[1:] == ["update-history-master", "--yes"]`, identical in effect to the argv the curl-piped form receives.
  2. `get-base.py` runs its own idempotent setup first regardless of how it was invoked (steps 1-4 below: resolve `repo_root` from cwd, add/fetch the `base` remote if missing, create-or-refresh the `.git/base-tools` worktree) — so even the local form works correctly on a repo that has never adopted `base` at all, not just as a shortcut once it's already set up.
  3. It then delegates (step 5) via `os.execvp` to the real `split.py` inside that worktree, forwarding `update-history-master --yes` unchanged plus `--repo-root <repo_root>` — i.e. this ends up literally running `update-history-master --yes` against the original repo. `--yes` there is `update_history_master`'s blanket flag that auto-confirms the "pull master?"/"pull base?" prompts (`history_master.py`'s `_prompt_yes_no`) instead of requiring an interactive terminal — needed here since `get-base.py` itself is meant to run non-interactively (e.g. piped from curl), so anything it delegates to shouldn't block on a prompt either.
- **Remote name is always literally `base`** — not configurable. This is deliberate: a fixed, unambiguous name so it's never confused with `origin` or some unrelated remote that happens to have its own branch called `base`. Only the *username/URL* is configurable.
- **Env var**: `BASE_GIT_USERNAME` (default `luckydonald`), building the URL `https://{BASE_GIT_USERNAME}@github.com/{BASE_GIT_USERNAME}/base.git` — matches the existing convention in `scripts/°base/git/remote/fix_username.py:20`'s `REQUIRED_REMOTES["base"]`.
- **Steps** (all idempotent — safe to "spam"):
  1. `repo_root = git rev-parse --show-toplevel` from cwd (error clearly if not inside a repo — never touches or requires any particular branch to be checked out).
  2. If the `base` remote doesn't exist (`git remote get-url base` fails), add it with the computed URL. If it already exists with a *different* URL, leave it alone (respect whatever's already configured) and just proceed — never overwrite.
  3. `git fetch base base` (the base repo's own main branch is itself named `base`, confirmed from this repo's own `git branch -a`/`base/base` naming throughout).
  4. Worktree path: fixed, deterministic, inside `.git/` so it needs no `.gitignore` entry and doesn't clutter the visible tree — `repo_root / ".git" / "base-tools"`. If it already exists as a valid worktree (`git -C <path> rev-parse --show-toplevel` succeeds and matches), just refresh it in place (`git -C <path> fetch base base && git -C <path> checkout --detach base/base`) rather than erroring on "path already exists." If it doesn't exist, `git worktree add --detach <path> base/base`.
  5. Delegate: `os.execvp(sys.executable, [sys.executable, str(worktree_path / "scripts" / "°base" / "git" / "split.py"), "--repo-root", str(repo_root), *sys.argv[1:]])` — hands off whatever subcommand/args the user passed straight to the real CLI, now reachable via the worktree, operating against the original repo via `--repo-root` (never against the worktree's own checkout).
- Never touches the currently checked-out branch or working tree in the target repo at all — the worktree is a wholly separate directory, and step 2/3 are remote-config/fetch only.

## Design

- **Fix in `sync_splits.py`**: in `sync_branch`, before calling `ensure_branch_started(history_ref, history_main_ref, cwd, dry_run=dry_run)`, check whether `history_ref` already exists (`git_ops.rev_parse(history_ref, cwd) is None`). If it's being created fresh (and not `dry_run`), write `refs/base-split/history-master-fork-point/{base_branch}` pointing at the resolved `history_main_ref` tip, using `git_ops.create_branch` (a plain ref-create, no commit). Use the same `FORK_POINT_REF_TEMPLATE` constant already defined in `history_master.py:34` — move it to a small shared location both files can import (simplest: define it once in `branches.py` alongside the other ref-naming helpers, since it's conceptually a "ref name for a branch" helper like `unclean_name`/`history_name`; `history_master.py` and `sync_splits.py` both import it from there instead of the constant being private to `history_master.py`).
- **New module `scripts/°base/git/°split_lib/bootstrap.py`**: `bootstrap_branch(base_branch: str, *, repo_root: Path, main_branch: str, dry_run: bool = False) -> dict`:
  1. Resolve `history_main_ref = branches.history_name(main_branch)`; if `git_ops.rev_parse(history_main_ref, cwd) is None`, return an error result telling the user to run `update-history-master` first (do not auto-run it — consistent with Phase 2's "skip + report, never auto-synthesize" principle already established in `rebase_to_master.py`).
  2. If `git_ops.rev_parse(base_branch, cwd) is None`, error: nothing to bootstrap from.
  3. If `ai/history/{base_branch}` doesn't exist yet: create it at `history_main_ref`'s tip via `git_ops.create_branch` (skip if `dry_run`), and write the fork-point ref (same helper as the `sync_splits.py` fix above, so both code paths that ever create a `history` branch fresh stay consistent).
  4. Call `sync_unclean.reconstruct_unclean(base_branch, repo_root=repo_root, main_branch=main_branch, dry_run=dry_run)` to build `ai/UNCLEAN/{base_branch}` — this is the already-working path, reused as-is.
  5. Return a combined result dict (history-branch-created bool, reconstruct_unclean's own result dict) for CLI reporting.
- **`cli.py`**: add a `bootstrap-branch <branch> [--dry-run]` subcommand calling `bootstrap.bootstrap_branch`. Also add a top-level `--repo-root <path>` option (before the subcommand, applying to all of them) that, when given, is passed through instead of calling `git_ops.repo_root()` with no args — this is what makes running the tool from a standalone clone against an unrelated target repo (the "never merged base" case above) ergonomic, instead of requiring the caller to `cd` into the target first.
- **Tests**: `scripts/°base/tests/test_git_split_bootstrap.py` — real temp repo with only a plain `feature` branch (real commits, no split branches at all): (a) errors clearly if `ai/history/master` doesn't exist yet; (b) after running `update-history-master`, bootstrapping creates `ai/history/feature` (empty, at history-master's tip) with the fork-point ref written, and `ai/UNCLEAN/feature` whose tree/content matches `feature`'s tip exactly; (c) `--dry-run` makes no ref changes; (d) running it twice is idempotent (second run is a no-op via `reconstruct_unclean`'s existing cursor logic). Also add one test in `test_git_split_sync_splits.py`-style coverage confirming the fork-point ref now gets written by `sync_branch` when it creates `ai/history/{branch}` fresh.
- **New regression test in `test_git_split_history_master.py`**: locks in the "`master` is never mutated by a base merge" invariant — construct a fake `base` remote with a conflicting file (same setup as the existing base-merge-recreation test), run `update-history-master` (first run, creating `ai/history/master` fresh and folding `base/base` into it), and assert `master`'s sha is byte-identical before and after (only `ai/history/master` moved).
- **New test `scripts/°base/tests/test_get_base.py`**: dynamic-import `get-base.py` (same `spec_from_file_location` pattern as other standalone scripts, e.g. `test_rebase_strip_claude_authorship.py`), using a real temp repo with a fake `base` remote (a second temp repo playing that role, matching the pattern in the history-master base-merge tests) instead of the real GitHub URL: (a) fresh repo, no `base` remote — running the script adds it, fetches, creates the worktree, and (mock `os.execvp`/`sys.exit` at the delegation boundary to avoid actually invoking `split.py` mid-test, asserting it *would* be called with the right argv) confirms delegation args; (b) re-running is a no-op on the remote-add step and refreshes (not recreates) the worktree; (c) an already-configured `base` remote with a different URL is left untouched; (d) running from a branch with real uncommitted changes in the working tree confirms nothing in the current checkout is touched (diff before/after is empty).
